# 通知配信サービス レート制限 設計書

| 項目 | 内容 |
|---|---|
| ステータス | ドラフト |
| 更新日 | 2026-11-01 |
| 対象 | 通知配信サービス（メール、プッシュ通知） |
| 作成者・レビュアー | 未定 |

## 概要

通知配信サービスにレート制限を入れる。制限は三つの単位で掛ける。依頼してくる呼び出し元、通知を受け取るユーザー、メールおよびプッシュの外部プロバイダである。状態は Redis に置き、トークンバケットで判定する。本番に入れる前に、制限を掛けずに判定結果だけを記録する期間を設ける。

## 背景

このサービスは、社内の他サービスからの依頼を受けてメールとプッシュ通知を送る。現時点で送信量を絞る仕組みはない前提で書く。これは未確認で、違っていれば「前提」の節を直す。

量の制御がないために、次の三つの問題が起こりうる。

1. 呼び出し元のバグや一括処理で依頼が急増すると、キューが埋まり、無関係な通知の配信が遅れる。
2. メールプロバイダとプッシュの配信先には送信量の上限がある。超えると依頼が拒否されるか、絞られる。拒否された通知は再送の対象になり、さらに量が増える。
3. 同じユーザーに短い時間で通知が集中する。ユーザーにとっては迷惑で、チャネルの利用停止につながる。

## ゴールとノンゴール

ゴールは次のとおり。

- 一つの呼び出し元の暴走が、他の呼び出し元の通知に影響しないようにする。
- 外部プロバイダの上限を超える送信を出さない。
- 同一ユーザーへの短時間の集中を抑える。
- 認証コードのように遅れると困る通知は、ユーザー単位の制限で止めない。
- 制限が働いた通知は、理由を後から追える。

ノンゴールは次のとおり。

- 課金や契約に基づく月次の送信枠の管理
- ユーザーごとの配信停止設定（オプトアウト）の扱い
- 重複送信の排除と冪等性（別の設計で扱う）
- 送信失敗時のリトライ方針の見直し

## 前提

次の点はこのチームで確認できていないので、前提として置く。

- 構成は「API で受け付け、キューに積み、ワーカーがプロバイダへ送る」形である。
- キューは遅延付きの再投入に対応している。
- Redis を新たに使える。既存の Redis を共用するかどうかは未定。
- 通知には、種別を表す `category` と、チャネル（`email` または `push`）が付いている。

## 設計

### 制限の単位

| 単位 | キー | 掛ける位置 | 守るもの |
|---|---|---|---|
| 呼び出し元 | `producer_id` × チャネル | API の受付時 | 他の呼び出し元の配信遅延 |
| 受信者 | `user_id` × チャネル × `category` | ワーカーの送信前 | ユーザーの体験 |
| プロバイダ | プロバイダ × 送信アカウント | ワーカーの送信直前 | プロバイダ上限と送信元の評価 |

呼び出し元の制限は受付時に掛ける。呼び出し元に 429 を返せば、その場で止まるためである。受信者とプロバイダの制限はワーカー側に置く。判定の結果、送信を遅らせる選択肢が必要になるからだ。

### アルゴリズム

トークンバケットを使う。バケットごとに容量と補充速度を持ち、通知一件につきトークンを一つ消費する。短い山は容量の範囲で通し、長い平均速度は補充速度で抑える。

判定は Redis の Lua スクリプト一回で行う。読み取り、補充の計算、消費を一つの原子的な操作にまとめ、ワーカーが複数台あっても二重に通さない。時刻は呼び出し側ではなく Redis の `TIME` を使い、ワーカー間の時計のずれを判定に入れない。スクリプトは「許可か否か」と、不許可の場合の「次にトークンが使えるまでのミリ秒」を返す。

キーは `rl:{単位}:{id}:{チャネル}:{category}` の形にする。バケットが満杯に戻るまでの時間の二倍を TTL にして、使われなくなったキーが残らないようにする。

### 超過したときの扱い

| 単位 | 超過時の動作 |
|---|---|
| 呼び出し元 | 依頼を受け付けず、`429 Too Many Requests` と `Retry-After` を返す |
| 受信者 | `category` の設定に従い、破棄するか遅延させる |
| プロバイダ | 送信を遅延させる。優先度の高い通知を先に処理する |

`category` ごとに次の二つを設定として持つ。

- `on_exceed`: `drop` か `delay`
- `bypass_user_limit`: 真なら受信者の制限を掛けない

認証コードやパスワード再設定のような通知は、`bypass_user_limit` を真にする。その場合も、呼び出し元とプロバイダの制限は掛かる。バイパスの抜け道にならないよう、真にできる `category` はレビューを通したものに限る。

`delay` の通知は、トークンが使えるようになる時刻まで遅延付きで再投入する。待ち時間が `category` ごとの `max_delay` を超えるなら送らず、状態を `expired` にする。古くなった通知を後から送っても、ユーザーには害になる。

どの場合も、通知の状態に `rate_limited`、`delayed`、`expired` のいずれかと、働いた制限の単位を記録する。問い合わせ API で参照できるようにする。

### 設定

制限値は設定ファイルで管理し、再起動なしで読み直せるようにする。構成は三層とする。

1. 全体の既定値
2. `category` ごとの値
3. 呼び出し元ごとの上書き

上書きは、正当な理由で量が多い呼び出し元のために用意する。変更はコードと同じレビューを通す。

初期値は設計の時点では決めない。次の節の計測期間で実際の流量を見てから置く。プロバイダの値だけは、各プロバイダの契約上の上限から割合で決める。割合は未定。

### Redis 障害時の挙動

Redis への問い合わせには短いタイムアウトを設け、値は実装時に決める。応答がない場合の動作は、単位ごとに変える。

- 呼び出し元の制限は、制限なしで通す。受付を止めると、障害が通知サービス全体の停止に広がる。
- 受信者の制限も、制限なしで通す。一時的な重複気味の送信は、通知が届かないよりましと判断する。
- プロバイダの制限は、ワーカーのプロセス内にある簡易バケットに切り替える。速度は全体の上限をワーカー台数で割った値とし、保守的に置く。外部の上限を超える害は他の二つより大きいためである。

Redis が使えなかった時間と、制限なしで通した件数はメトリクスに出す。

## API の変更

受付 API が 429 を返すようになる。レスポンスには `Retry-After` を付ける。既存の呼び出し元がこのステータスを再試行できるかは未確認で、ロールアウト前に呼び出し元の一覧を作って確認する。

通知の状態取得 API には、先に述べた状態値と `limited_by`（`producer`、`user`、`provider`）を加える。既存のフィールドは変えない。

## 観測

メトリクスは単位とチャネルと `category` のラベルを付けて出す。

- 許可数、遅延数、破棄数、期限切れ数
- 遅延した通知の待ち時間の分布
- プロバイダのバケットの残トークン
- Redis 呼び出しのエラー数と、制限なしで通した件数

制限が働いた通知は、通知 ID、単位、キー、判定結果をログに残す。ユーザー ID はキーに含まれるので、ログの保管期間は既存の通知ログに合わせる。

アラートは三つ置く。プロバイダのバケットが長く枯渇している状態、遅延キューの滞留が増え続けている状態、Redis のエラーが続いている状態。しきい値は計測期間のあとに決める。

## ロールアウト

単位ごとにフラグを持ち、段階的に有効にする。

1. 観測のみ。判定して記録するが、通知は止めず、遅らせもしない。期間は流量の周期が一巡する長さを取る（日次と週次の山を含める）。
2. 観測結果から制限値を決める。計測では、各制限があれば何件が止まったかを見て、止まる件数が想定外に多い `category` は値を見直す。
3. プロバイダの制限を有効にする。ユーザーに見える変化は遅延だけで、影響が最も小さい。
4. 呼び出し元の制限を有効にする。事前に 429 の扱いを呼び出し元と確認しておく。
5. 受信者の制限を `category` ごとに有効にする。

戻すときは該当のフラグを切る。フラグを切れば、その単位は制限のない状態に戻る。バケットのキーは TTL で消える。

## テスト

- Lua スクリプトの単体テスト。補充の境界、容量いっぱいの消費、`cost` が残量を超える場合を確認する。
- 並行実行のテスト。複数のワーカーから同じキーを叩き、通した総数が容量と補充量の合計を超えないことを確認する。
- 障害注入のテスト。Redis を止めたときに、単位ごとの動作が前節のとおりになることを確認する。
- 負荷テスト。呼び出し元の暴走を模した流量で、他の呼び出し元の配信遅延が増えないことを確認する。
- `bypass_user_limit` のテスト。バイパス対象の `category` が、受信者の制限を受けずにプロバイダの制限だけを受けることを確認する。

## 検討した代替案

| 案 | 採らない理由 |
|---|---|
| 固定ウィンドウ | ウィンドウの境目で、上限の二倍が通る |
| スライディングウィンドウ（ログ方式） | 保持するデータ量が流量に比例して増える |
| ワーカーのメモリ内だけで制限 | 台数が変わると全体の上限が変わる。ユーザー単位の制限は台数分に散らばる |
| API ゲートウェイの制限だけに頼る | 受信者単位とプロバイダ単位の判定ができない |

## 未決事項

- キューが遅延付きの再投入に対応しているか。対応していなければ、遅延用の別の仕組みが要る。
- 各プロバイダの契約上の上限と、超過したときの挙動。
- `category` の一覧と、それぞれの `on_exceed` と `bypass_user_limit` を誰が決めるか。
- Redis を新規に立てるか、既存を共用するか。
- 既存の呼び出し元が 429 を再試行できるか。
- 制限値の初期値。観測期間のデータが出てから決める。
