## 1. 概要

現在、Feature Flag は各サービスの設定ファイル（YAML / JSON / `.env`）にハードコードされている。フラグを切り替えるにはコード変更、レビュー、ビルド、デプロイが必要になる。本 RFC では、フラグの定義・評価・配信・監査を一元管理する社内 Feature Flag サービス（以下 **Flagd**、仮称）を構築し、既存の設定ファイルベースのフラグを段階的に移行することを提案する。

## 2. 背景と課題

### 2.1 現状

- フラグは各リポジトリの `config/*.yaml` や環境変数で `true` / `false` として定義されている。
- 環境ごと（dev / staging / prod）に別ファイルで値を管理している。
- 割合ロールアウトやユーザー単位のターゲティングは、サービスごとに独自実装しているか、そもそも存在しない。

### 2.2 課題

1. **切り替えが遅い**: フラグの変更には PR 作成からデプロイ完了まで、通常 30〜90 分かかる。障害時のキルスイッチとして機能しない。
2. **リスクの高いリリース**: 段階的ロールアウト（1% → 10% → 100%）ができず、新機能は全ユーザーに一斉公開される。
3. **可視性がない**: 「本番で今どのフラグが有効か」をサービス横断で確認する手段がない。
4. **監査が不十分**: 誰がいつ何のためにフラグを変えたかが Git 履歴に散らばっており、追跡しにくい。
5. **フラグの残骸**: 役目を終えたフラグが削除されずに残り、コードの分岐が増え続けている。
6. **実装の重複**: 複数チームが似たようなターゲティングロジックを別々に実装・保守している。

## 3. ゴールと非ゴール

### 3.1 ゴール

- デプロイなしでフラグを変更でき、変更が **10 秒以内（p99）** に全インスタンスへ反映される。
- 真偽値・文字列・数値・JSON の各フラグ型をサポートする。
- ターゲティングルール（ユーザー ID、テナント、属性、割合ロールアウト）をサポートする。
- フラグの変更をすべて監査ログに記録し、権限で制御する。
- サービスが停止してもアプリケーションの動作を妨げない（フェイルセーフ）。
- 主要言語（Go / TypeScript / Python / Java）向けの公式 SDK を提供する。
- フラグのライフサイクル（作成〜削除）を管理し、古くなったフラグを検出する。

### 3.2 非ゴール

- 本格的な A/B テスト基盤（統計解析・実験設計）。これは将来の拡張として、評価イベントを既存の分析基盤へ送る形に留める。
- 任意の設定値（タイムアウト値、接続先 URL など）を管理する汎用 config サービス。
- クライアントサイド（ブラウザ / モバイル）での直接評価。これはフェーズ 3 で別途検討する。

## 4. 提案

### 4.1 全体アーキテクチャ

```
┌──────────────┐      ┌─────────────────────────────┐
│  Admin UI /  │─────▶│        Flagd Control Plane   │
│  CLI / API   │      │  - Flag CRUD / RBAC / Audit  │
└──────────────┘      │  - PostgreSQL（正本）         │
                      └──────────────┬──────────────┘
                                     │ 変更イベント
                                     ▼
                      ┌─────────────────────────────┐
                      │       Flagd Relay（配信層）   │
                      │  - SSE / gRPC stream         │
                      │  - スナップショット配信        │
                      └──────────────┬──────────────┘
                                     │
              ┌──────────────────────┼──────────────────────┐
              ▼                      ▼                      ▼
     ┌────────────────┐    ┌────────────────┐    ┌────────────────┐
     │ Service A + SDK│    │ Service B + SDK│    │ Service C + SDK│
     │ （ローカル評価） │    │ （ローカル評価） │    │ （ローカル評価） │
     └────────────────┘    └────────────────┘    └────────────────┘
```

主な設計判断は次の 2 点。

- **ローカル評価**: SDK はフラグ定義全体（ルールを含む）をメモリに保持し、評価をプロセス内で行う。評価のたびにネットワーク呼び出しは発生しない。
- **Control Plane と配信層の分離**: Control Plane が落ちても、Relay と SDK は最後に受け取ったスナップショットで動き続ける。

### 4.2 データモデル

```yaml
key: checkout.new-payment-flow        # <domain>.<feature> 形式、一意
type: boolean                          # boolean | string | number | json
description: "新決済フローへの切り替え"
owner: team-payments
lifecycle: release                     # release | ops | experiment | permission
expires_at: 2027-03-31                 # release / experiment では必須
variants:
  on: true
  off: false
environments:
  production:
    enabled: true
    default_variant: off
    rules:
      - name: internal-users
        match: { attribute: email, op: ends_with, value: "@example.co.jp" }
        variant: on
      - name: gradual-rollout
        rollout: { on: 10, off: 90 }   # パーセンテージ
        bucket_by: user_id
  staging:
    enabled: true
    default_variant: on
```

**ライフサイクル種別**

| 種別 | 用途 | 有効期限 |
|---|---|---|
| `release` | 新機能の段階的公開 | 必須（最長 90 日） |
| `ops` | キルスイッチ、負荷制御 | 任意（長期保持可） |
| `experiment` | 実験・比較 | 必須 |
| `permission` | プラン / テナント別の機能開放 | 任意 |

### 4.3 評価のセマンティクス

1. 対象環境で `enabled: false` の場合は `default_variant` を返す。
2. `rules` を上から順に評価し、最初に一致したルールの variant を返す。
3. どのルールにも一致しなければ `default_variant` を返す。
4. 割合ロールアウトでは `hash(flag_key + salt + bucket_by値) mod 100` で決定的にバケットを割り当てる。割合を増やしても、すでに `on` になったユーザーは `on` のまま維持される。

### 4.4 SDK

API は [OpenFeature](https://openfeature.dev/) 仕様に準拠し、Flagd を OpenFeature Provider として実装する。これにより、将来ベンダー製品へ移行する場合もアプリケーションコードを変えずに済む。

```go
client := openfeature.NewClient("checkout-service")
ctx := openfeature.NewEvaluationContext(userID, map[string]any{
    "email":  user.Email,
    "tenant": user.TenantID,
})
if client.Boolean(reqCtx, "checkout.new-payment-flow", false, ctx) {
    // 新フロー
}
```

SDK に求める要件は以下のとおり。

- 起動時に Relay からスナップショットを取得し、以降はストリームで差分を受け取る。
- **フォールバックの優先順位**: メモリ上の最新値 → ローカルディスクのキャッシュ → ビルド時に同梱したスナップショット → コード上のデフォルト値。
- 評価のレイテンシは p99 < 50µs（ネットワーク I/O なし）。
- 評価メトリクス（フラグ・variant ごとの評価回数）をサンプリングして非同期に送信する。

### 4.5 配信（Relay）

- Control Plane がフラグを更新すると、Postgres の `LISTEN/NOTIFY` を通じて Relay に通知し、Relay が接続中の SDK へ SSE（または gRPC stream）で差分を配信する。
- 各スナップショットには単調増加する `version` を付ける。SDK は再接続時に `since=<version>` を送り、取りこぼしを防ぐ。
- Relay はステートレスに作り、各リージョンに 3 台以上配置して水平にスケールする。
- 環境ごとに SDK キーを発行する。キーはサーバー専用で、読み取りしかできない。

### 4.6 管理 UI / API / CLI

- フラグの作成・編集・ロールアウト割合の変更・有効化と無効化ができる。
- **本番環境での変更**には変更理由の入力を必須とする。`release` 以外のフラグは、オプションで 2 人承認を設定できる。
- 指定時刻に割合を引き上げるスケジュール機能を提供する。
- CLI（`flagctl`）と Terraform Provider を提供し、フラグ定義を GitOps で管理することも選べるようにする。

### 4.7 権限と監査

| ロール | 権限 |
|---|---|
| Viewer | 全フラグの閲覧 |
| Editor | 自チームが owner のフラグを dev / staging で編集 |
| Releaser | 自チームが owner のフラグを production で編集 |
| Admin | 全フラグの編集、ロール管理 |

- 権限は社内 SSO（OIDC）のグループに連動させる。
- 監査ログには、変更者・時刻・変更前後の差分・理由を記録し、2 年間保持する。
- 本番での変更は Slack の `#flag-changes` に通知し、既存のインシデント管理ツールのタイムラインにもイベントとして送る。

### 4.8 フラグの衛生管理

- `expires_at` を過ぎたフラグは、owner チームへ週次で通知する。
- 30 日以上評価されていないフラグには「未使用」ラベルを付ける。
- CI 用の静的解析ツールでコード中のフラグ参照を検出し、Flagd 側に存在しないキーを参照していたらエラーにする。
- フラグを削除する際は、コード上の参照がゼロであることを確認してから行う。

## 5. 非機能要件

| 項目 | 目標 |
|---|---|
| 変更の反映時間 | p99 < 10 秒 |
| 評価レイテンシ（SDK 内） | p99 < 50µs |
| Relay の可用性 | 99.95% |
| Control Plane の可用性 | 99.9%（停止中も評価は継続できる） |
| 規模 | フラグ 5,000 件、同時接続 SDK 20,000 |
| スナップショットのサイズ | 1 環境あたり < 5MB |

## 6. 障害時の挙動

| 障害 | 影響 | 挙動 |
|---|---|---|
| Control Plane 停止 | フラグを変更できない | 評価は最後のスナップショットで継続する |
| Relay 全台停止 | 変更が反映されない | SDK はメモリ上の値で継続し、指数バックオフで再接続する |
| 停止中に SDK が起動 | 初期値を取得できない | ディスクキャッシュ、同梱スナップショット、コード上のデフォルト値の順にフォールバックする |
| 不正なルールの投入 | 誤った評価結果 | 保存時にスキーマを検証する。ワンクリックで直前のバージョンへロールバックできる |

## 7. 移行計画

### フェーズ 0: 準備（4 週間）
- Control Plane、Relay、Go / TypeScript SDK の MVP を作る。
- 既存の設定ファイルからフラグを抽出してインポートするツール `flag-import` を作る。

### フェーズ 1: パイロット（4 週間）
- パイロットチームを 2 つ選び（例: Payments、Search）、新規フラグを Flagd で作成する。
- 既存フラグは **デュアルリード** で移行する。SDK で評価しつつ設定ファイルの値とも比較し、差異をログに出す。

### フェーズ 2: 全社展開（12 週間）
- Python / Java の SDK を提供する。
- 各チームの既存フラグを移行する（チームごとの移行チェックリストを用意する）。
- 新規フラグを設定ファイルに追加することを lint で禁止する。

### フェーズ 3: 完了と拡張
- 設定ファイル内のフラグ定義を削除する。
- クライアントサイド SDK（評価結果のみ配信する方式）と、実験基盤との連携を検討する。

**成功指標**

- フラグ変更にかかる時間の中央値: 45 分 → 1 分未満
- 段階的ロールアウトを経てリリースされた機能の割合: 70% 以上
- フラグ起因のロールバックデプロイ件数: 50% 削減
- 期限切れフラグの数: 四半期ごとに減少

## 8. 代替案

### 8.1 SaaS の採用（LaunchDarkly、Unleash Cloud など）
- **利点**: 構築が不要で、機能が豊富。
- **欠点**: シート課金や MAU 課金で、年間コストが大きくなりうる。ユーザー属性を外部へ送ることになり、データ所在地の要件を満たせるか確認が必要。
- **判断**: コスト見積もりとセキュリティ審査の結果を比較材料として付録に添付する（#TODO(agent): 見積もりを取得して付録 A に記載する）。OpenFeature に準拠しておくことで、将来乗り換える余地を残す。

### 8.2 OSS のセルフホスト（Unleash、Flagsmith、flagd）
- **利点**: 構築にかかる工数が小さい。
- **欠点**: 社内 SSO や RBAC、監査要件に合わせてカスタマイズが必要。運用は結局自分たちで負うことになる。
- **判断**: **有力候補**。フェーズ 0 で PoC を行い、要件を満たすなら自作をやめて OSS を採用する。本 RFC の設計は、その評価基準としても使う。

### 8.3 現状維持 + 設定ファイルのホットリロード
- **利点**: 変更が最小限で済む。
- **欠点**: ターゲティング、監査、横断的な可視性という課題が解決しない。
- **判断**: 不採用。

## 9. セキュリティとプライバシー

- SDK はユーザー属性をローカルで評価するだけで、Flagd へは送信しない。評価メトリクスにも PII を含めない。
- SDK キーは既存のシークレット管理基盤で配布し、ローテーションできるようにする。
- Admin API は社内ネットワークからのみアクセスでき、SSO による認証を必須とする。

## 10. コストと体制

- **構築**: Platform Team のエンジニア 2 名 × 約 2 四半期（OSS を採用する場合は約 1 四半期）
- **運用**: Platform Team が所有し、SLO とオンコールを定義する。
- **インフラ**: Postgres（HA 構成）1 系統、Relay は各リージョンに 3 台以上。

## 11. 未解決の論点

1. 自作するか OSS（Unleash / flagd）を採用するか。フェーズ 0 の PoC 結果をもとに決める。
2. 本番変更の 2 人承認を、どのライフサイクル種別で必須にするか。
3. GitOps（Terraform）と UI の両方で編集できる場合、どちらを正とするか。
4. バッチジョブなど短時間で終わるプロセス向けに、ストリーム接続ではなくスナップショットの単発取得モードが必要か。
