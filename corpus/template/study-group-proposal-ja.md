## 1. 背景と目的

業務が忙しくなると、知識の共有は個人の裁量に任されがちです。その結果、特定の人しか分からない仕組みが増え、勉強会を開きたい人の負担も大きくなります。

本制度は、エンジニアが業務時間の一部を使って学び、学びを社内に還元する場を継続的に用意することを目的とします。

- 技術的な知見を組織内で共有し、属人化を減らす
- 新しい技術や手法を試す機会を、業務とは別に確保する
- 社内での発表や議論を通じて、技術的なコミュニケーション力を育てる

## 2. 制度の概要

| 項目 | 内容（案） |
|---|---|
| 制度名 | 〔例: エンジニア・ラーニング・アワー〕 |
| 実施頻度 | 月2回、1回あたり60分 |
| 形式 | 発表（30分）と質疑・議論（30分） |
| 参加形式 | 対面（会議室）とオンラインの併用 |
| 記録 | 発表資料と録画を社内wikiに保存 |
| 発表者 | 参加者から募集。1人1年1回を上限の目安とする |

### 発表テーマの例

- 自社システムの設計判断とその背景
- 障害の振り返りから得た教訓
- 外部の技術書や論文の要点整理
- 新しいツールや言語機能の試行結果
- 採用した手法を見直した経緯

## 3. 対象者

- 対象: 開発に関わる全社員（職種・経験年数は問わない）
- 参加: 任意。ただし、発表者には業務時間内での準備時間を認める
- 外部の方の参加: 〔社外秘情報を扱わない範囲で可とするか、要決定〕

## 4. 運営体制

| 役割 | 担当 | 主な業務 |
|---|---|---|
| 事務局 | 〔部署名〕 | 日程調整、会場・配信の手配、記録の保存 |
| 企画担当 | 有志2名程度 | テーマ選定、発表者への相談、振り返り |
| 発表者 | 参加者 | 資料作成、当日の発表 |
| 承認者 | 〔エンジニアリングマネージャー等〕 | 制度の方針判断、予算の承認 |

運営の負荷が特定の人に偏らないよう、企画担当は半年ごとに交代します。

## 5. 年間スケジュール（案）

| 時期 | 内容 |
|---|---|
| 11月 | 制度の承認、予算の確保、運営メンバーの決定 |
| 12月 | 社内告知、発表テーマの募集 |
| 1月〜 | 第1回の開催（以降、月2回のペース） |
| 3か月ごと | 参加状況と満足度の確認、運用ルールの見直し |
| 6か月ごと | 企画担当の交代、制度全体の評価 |

## 7. 成果指標（KPI）

定量と定性の両方で評価します。目標値は導入後3か月で設定し直します。

| 指標 | 測定方法 | 目安 |
|---|---|---|
| 開催回数 | 事務局の記録 | 月2回を維持 |
| 参加率 | 参加登録と当日の出席記録 | 対象者の 〔 〕% 以上 |
| 発表者数 | 発表記録 | 半年で 〔 〕名以上 |
| 満足度 | 開催後のアンケート（5段階） | 平均 4.0 以上 |
| 社内wikiの閲覧数 | wikiの統計 | 録画・資料の閲覧が増えているか |
| 知識共有の変化 | 四半期ごとのアンケート | 「質問先が分からない」と答える人が減っているか |

## 8. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 繁忙期に開催できなくなる | 制度が形骸化する | 開催を一時的に月1回へ落とすルールを設け、中止にはしない |
| 発表者が固定化する | 参加者の偏りが生まれる | 発表者の募集を全社向けに継続し、新規発表者を優先する |
| 内容が社外秘に触れる | 情報漏えいにつながる | 発表前に資料を確認するチェックリストを用意する |
| 参加が義務と受け止められる | 心理的負担が増える | 参加は任意と明記し、評価制度とは連動させない |
| 運営が特定の人に集中する | 担当者が疲弊する | 企画担当を半年ごとに交代し、事務局の作業を手順書化する |

## 9. 導入ステップ

1. 企画書の承認を得る（〔承認者〕）
2. 運営メンバーを決め、初回の発表者に打診する
3. 社内に告知し、発表テーマを募集する
4. 第1回を開催し、参加者の感想を集める
5. 感想をもとに、形式や時間配分を調整する
6. 3か月後に指標を確認し、制度を継続するか判断する

## 10. 承認前に決めたい事項

- 業務時間内での開催を認めるか（認める場合、対象時間と範囲）
- 発表準備の時間を勤務時間として扱うか
- 社外の方を招くか、社外秘情報の扱いをどうするか
- 予算の上限と、発表者への謝礼を設けるか
- 制度の所管部署をどこにするか
